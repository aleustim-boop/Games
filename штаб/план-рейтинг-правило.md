## 1. Опись — как устроено сейчас (по факту кода)

### 1.1 Откуда берётся признак правила партии

- `server/комнаты.js`, поле `комната.переводной` — булево, задаётся при
  создании/настройке стола (строки 891–892, 1072, 2200–2201, 2370). Он же
  используется в `застольеДляРейтинга` при передаче поля `парами` (строка 2325)
  и в текстовом описании стола (строка 3534: `«Переводной»`/`«Подкидной»`).
- Партии **без сети** (в браузере с ботом) идут через `server/билеты.js`.
  Функция `выдать(номер, игра, уровень, сейчас)` (строка 129) НЕ принимает
  признак правила вообще — билет несёт только номер игрока, игру и уровень
  бота. `застолье`, которое строит `погасить()` (строки 201–206), тоже не
  содержит поля про правило. Это значит: если у игры «дурак» есть выбор
  подкидной/переводной ещё и в одиночной игре с ботом (не через комнату) —
  этот путь сейчас вообще не знает, по какому правилу играли, и его придётся
  либо тоже научить передавать правило, либо сознательно решить, что
  партии с ботом в браузере не делятся по правилу (они и так не идут
  в общий подсчёт «стол по сети», а списываются отдельным способом).
  Это отдельный вопрос вне уже найденного штабом места (`комнаты.js`),
  требует уточнения у владельца — есть ли вообще выбор подкидной/переводной
  в одиночной игре с ботом.

### 1.2 `server/комнаты.js` — где признак есть, но не доходит до рейтинга

- `учестьИтогПартии(комната)` (строки 2282–2294) — единственное место,
  откуда вызывается `рейтинг.учестьПартию(комната.игра, застольеДляРейтинга(комната))`
  (строка 2293), при доигранной или ничейной партии.
- `застольеДляРейтинга(комната)` (строки 2309–2334) формирует на каждого
  игрока объект `{ номер, имя, этоБот, парами, уровень, победил, ничья }`.
  Поле `парами: комната.парами === true` уже прокинуто (комментарий в коде
  строки 2320–2325 объясняет, зачем это берётся из комнаты, а не угадывается
  по форме стола). Поля `переводной` в этом объекте **нет**, хотя
  `комната.переводной` в этот момент уже существует и используется парой
  строк ниже для другого — текстовой подписи стола (3529–3534).
- Само поле `парами` дальше в `рейтинг.учестьПартию` **тоже никак не
  используется** (см. 1.3) — оно приходит в объект застолья, но
  `server/рейтинг.js` его не читает вовсе. Похоже, `парами` сейчас передаётся
  только ради стыковки со второй мерой — «силой» (`server/сила-игроков.js`,
  которую `учестьПартию` вызывает первой строкой, «сила.учесть(игра, застольем)» —
  не открывал этот файл, он не в списке задания, но по имени поля и
  комментарию в шапке `рейтинг.js` («парами считается вполовину») это похоже
  на его потребителя). Это значит: у нас уже есть прецедент «поле в застолье
  для одного потребителя (силы), не для другого (очков)» — по аналогии
  «переводной» можно добавить в застолье и использовать только там, где
  нужно, не трогая тех, кому оно не надо.

### 1.3 `server/рейтинг.js` — хранилище: один агрегат на игрока на игру

- Память: `таблицы` — `Map(имяИгры → Map(номер → запись))` (строка 164).
  Внутри игры — ОДНА запись на игрока, без какой-либо второй оси.
- `пустаяЗапись(номер)` (строки 202–223) — поля: `номер, имя, очки, побед,
  ничьих, партий, деньБотов, очкиОтБотовЗаДень, деньЛюдей,
  очкиОтЛюдейЗаДень, партийСЧеловекомЗаДень, последняяИгра`. Про правило
  партии (подкидной/переводной) — ничего, `парами` тоже нигде не хранится
  (используется по пути мимо, только для силы).
- Формат файла на диске (`рейтинг.json`, путь — `гдеДанные.файл('рейтинг.json')`,
  строка 104): плоский список объектов `{ игра, номер, имя, очки, побед,
  ничьих, партий, деньБотов, очкиОтБотовЗаДень, деньЛюдей,
  очкиОтЛюдейЗаДень, партийСЧеловекомЗаДень, последняяИгра }` — см.
  `записатьСейчас()` (строки 263–293).
- Чтение старого файла уже устроено терпимо: `загрузить()` (строки 230–260)
  собирает `свежая = пустаяЗапись(...)` и переносит поля ПО ОДНОМУ с явной
  проверкой типа и подстановкой значения по умолчанию, если поля в старой
  записи нет (`Number(запись.очки) || 0` и т.п.). Это готовый шаблон для
  обратной совместимости: если добавить новые поля (например,
  `поПравилу: { подкидной: {...}, переводной: {...} }`), старые записи без
  этого поля должны просто получать пустой под-агрегат, а не падать.
  Уже есть тест на этот случай — `tests/очки-рейтинга.js`, пункт 6
  («старый файл рейтинга, где новых полей ещё нет, читается и не теряет
  накопленное») — его нужно будет расширить, а не писать с нуля.
- Начисление идёт в `учестьПартию(игра, застольем)` (строки 417–462): для
  каждого игрока из застолья находит/заводит `запись` через `записьИгрока`,
  инкрементирует `партий`, `побед`/`ничьих`, дальше для каждого соперника
  за столом зовёт `начислить(запись, откуда, сколько, сегодня)` — которая
  прибавляет прямо в `запись.очки` (строки 370, 380) с оглядкой на суточные
  потолки (`деньБотов`/`деньЛюдей`, тоже прямо в `запись`).
- Отдача клиенту: `срезДляИгрока(игра, номер)` (строки 520–560) через
  `строка(запись, место, этоЯ)` (504–513) — отдаёт `{место, имя, очки, побед,
  партий, этоЯ}`. Про правило — ничего; сортировка (`порядок(игра)`,
  488–498) сортирует по единственному общему `очки`.

### 1.4 `server/сервер.js` — где сервер отдаёт рейтинг клиенту

- Маршрут `POST /рейтинг` → `таблицаРейтинга(тело, ответ)` (строки 2427–2459).
  Тело запроса сейчас читает только `{ игра, initData }` (строка 2428–2429).
  Признака правила во входе нет вовсе — фильтр «Подкидной/Переводной»
  сегодня физически некуда передать на сервер, даже если бы кнопки на
  экране были живыми.
  Ответ собирается вручную полем за полем (строки 2445–2458): `ок,
  узналиВас, игра, всего, яВТаблице, я, верхушка, вокругМеня, сила` — это
  прямая передача полей из `рейтинг.срезДляИгрока(игра, кто)`. Значит,
  если `срезДляИгрока` научится принимать/отдавать отдельный срез по
  правилу, `таблицаРейтинга` в сервере — то самое место, где нужно
  прокинуть новый параметр запроса и, возможно, новое поле ответа.
- Второй потребитель рейтинга — `server/билеты.js` → `рейтинг.учестьПартию`
  (без правила, см. 1.1) и `рейтинг.осталосьОтБотовСегодня` (не относится
  к правилу, только к суточному потолку от ботов).

### 1.5 `js/рейтинг-экран.js` — что сейчас с переключателями

- Три пары переключателей рисуются функцией `блокФильтровДурака()`
  (строки 1151–1157) через `параФильтра(метка, левый, правый)` (1135–1143)
  и `вариантФильтра(текст, выбран)` (1118–1133): **левый вариант каждой
  пары захардкожен как «выбран» (`true`), правый — как «не выбран»
  (`false`), и ОБА варианта получают `кнопка.disabled = true`** (строка
  1124) независимо от того, выбран вариант или нет. У невыбранного варианта
  дополнительно рисуется пометка `«скоро»` (1126–1131).
  Три пары: `('Круг игроков', 'Все игроки', 'Друзья')`,
  `('Правила дурака', 'Подкидной', 'Переводной')`,
  `('Состав игроков', 'Личный', '2 на 2')`.
- Показ/скрытие всего блока — `отметитьИгру(игра)` (1288–1298): блок
  фильтров скрыт классом `скрыт`, если открыта не игра «дурак». У шашек,
  шахмат, нард блока фильтров нет вовсе.
- **Ни один из трёх переключателей никак не подключён к запросу данных.**
  `вариантФильтра` не вешает `addEventListener` (кнопки `disabled`, и в
  разметке для них нет обработчика клика вовсе — только `кнопка.disabled = true`
  и текст). Функция, которая ходит на сервер, — `спроситьТаблицу(игра,
  сколькоЖдать)` (строки 218–261) — принимает только `игра` и не читает
  никакого состояния фильтров; тело запроса — `{ игра: игра, initData:
  подписьTelegram() }` (строка 237). Значит, чтобы фильтр «Подкидной/
  Переводной» ожил, нужно: 1) завести переменную состояния (по аналогии
  с `мераСейчас`), 2) снять `disabled` только у СРЕДНЕЙ пары (первая —
  «Друзья», третья — «2 на 2» — вне рамок этой задачи, см. ниже),
  3) повесить обработчик клика, который меняет состояние и заново зовёт
  `обновить(играСейчас)`, 4) прокинуть выбранное правило в тело запроса
  `спроситьТаблицу`, 5) очистить кэш `последнийОтвет`/`готовыйОтвет` —
  сейчас кэш всего на 30 секунд хранится по игре (`играОтвета`), без учёта
  правила: если добавить фильтр, ответ с одним правилом не должен
  подсовываться при переключении на другое — либо кэш ключить парой
  (игра, правило), либо сбрасывать при переключении фильтра, как уже
  делает `показатьМеру` при переключении силы/очков (строки 1312–1319) —
  но там кэш переиспользуется, потому что обе меры едут ОДНИМ ответом;
  для правила так не выйдет без изменения формата ответа сервера (см. 2.4).

## 2. План маленькими этапами

Каждый этап — 1–2 файла, один исполнитель на файл. Порядок важен:
хранилище раньше передачи признака, признак раньше отдачи клиенту,
клиент — последним.

### Этап 1 — `server/рейтинг.js`: вторая ось счётчиков в записи игрока
Файл: `server/рейтинг.js` (один исполнитель).
- Добавить в `пустаяЗапись` под-объект вида `поПравилу: { подкидной:
  {очки, побед, ничьих, партий}, переводной: {очки, побед, ничьих,
  партий} }` (общий счёт — существующие плоские поля — НЕ трогать и не
  переносить).
- `учестьПартию` — если объект застолья несёт новое поле правила (см.
  этап 2), параллельно с общим счётом обновлять соответствующий
  под-агрегат тем же самым начислением (те же цены, тот же дневной
  потолок или отдельный — решить отдельно, видимо взять тот же общий
  потолок, чтобы не плодить вторую систему ограничителей; уточнить
  у штаба/владельца, не решать самому).
- `загрузить()` — читать `поПравилу` с защитой: нет поля или оно не
  объект → подставлять пустые нулевые счётчики (по образцу того, как уже
  читаются `деньБотов`/`партийСЧеловекомЗаДень`). Партии, сыгранные ДО
  этой правки, у которых в файле такого поля нет и не может быть, — это
  и есть «начинаем с нуля», как решил владелец.
- `записатьСейчас()` — писать новое поле в файл.
- `срезДляИгрока`/`строка` — новый необязательный параметр «правило»,
  который, если задан, сортирует и отдаёт данные из под-агрегата вместо
  общего (обсудить с штабом, отдавать ли общий и по правилу одним ответом
  или разными запросами — влияет на этап 4).
- Риск: это НЕ рисковый в смысле сети файл, но именно тут живёт
  реальная опасность потерять уже накопленные очки — **нужен ревьюер**
  обязательно (сервер, общий файл, правило проекта требует ревью на
  рисковом месте).

### Этап 2 — `server/комнаты.js`: прокинуть признак правила в застолье
Файл: `server/комнаты.js` (один исполнитель, отдельно от этапа 1).
- В `застольеДляРейтинга` добавить поле `переводной: комната.переводной
  === true` в объект на каждого игрока (по образцу уже существующего
  `парами`).
- Не трогать `учестьИтогПартии` и остальную логику вокруг — только это
  поле.
- Не трогать `server/билеты.js` в этом этапе (см. открытый вопрос 1.1) —
  решить отдельно, входит это в рамки задачи или нет.
- Нужен ревьюер (правило проекта: сервер — рисковое место всегда).

### Этап 3 — `server/сервер.js`: принять фильтр от клиента, отдать новое поле
Файл: `server/сервер.js` (один исполнитель).
- `таблицаРейтинга(тело, ответ)` — прочитать из `тело` необязательное
  поле, например `правило` (`'подкидной'|'переводной'|undefined`), с
  проверкой значения (мусор → игнорировать, как игра по умолчанию
  приводится к «дурак»).
- Передать это значение в `рейтинг.срезДляИгрока(игра, кто, правило)`
  (сигнатура — то, что решит этап 1) и вернуть результат тем же
  «вручную поле за полем» способом, что и сейчас.
- Нужен ревьюер (сервер, рисковое место).

### Этап 4 — `js/рейтинг-экран.js`: снять disabled со средней пары, подключить к данным
Файл: `js/рейтинг-экран.js` (один исполнитель).
- Снять `disabled` и пометку «скоро» ТОЛЬКО у пары «Подкидной/Переводной»
  (первая пара «Все игроки/Друзья» и третья «Личный/2 на 2» — вне рамок,
  остаются как есть, disabled, «скоро»).
- Завести переменную состояния (аналог `мераСейчас`), повесить обработчик
  клика на обе кнопки пары, при переключении вызывать `обновить(играСейчас)`
  заново с новым параметром в `спроситьТаблицу`.
- Поправить кэш `последнийОтвет`/`играОтвета` — либо ключить его парой
  (игра, правило), либо сбрасывать при переключении фильтра (см. 1.5,
  пункт 5) — решить по факту формата ответа сервера из этапа 3.
- Тестировщику потом нужно прогнать `tests/новые-кнопки-и-рейтинг.js` и
  `tests/рейтинг-экран-четыре-игры.js` (уже существующие, судя по именам,
  проверяют именно эти кнопки и экран) — проверить, что они не покраснели
  от смены `disabled`.
- Ревью не обязательно (правило проекта — сервер обязателен, клиентский
  файл рисования — по решению штаба, риск ниже).

### Что проверяет тестировщик отдельно (не разработчик)
- Главное: **старые записи `рейтинг.json` без поля `поПравилу` — после
  правки этапа 1 продолжают читаться с прежними очками, никто ничего
  не теряет.** Расширить существующий `tests/очки-рейтинга.js` (там уже
  есть пункт 6 именно про старый формат — готовый шаблон подхода, не
  писать с нуля).
- Начисление в под-агрегат идёт синхронно с общим (сыграл партию
  подкидным — выросли оба счётчика: общий и «подкидной», а «переводной»
  не тронут).
- Запрос `/рейтинг` с параметром `правило` и без него — оба случая живые,
  без параметра ведёт себя как раньше (обратная совместимость по сети,
  не только по файлу).
- Браузерная проверка `tests/новые-кнопки-и-рейтинг.js` /
  `tests/рейтинг-экран-четыре-игры.js` — что средняя пара кнопок стала
  живой, а остальные две пары остались честно «скоро».

## 3. Явно вне рамок этого плана
- Командный режим 2 на 2 — как считать рейтинг парами, это отдельный
  нерешённый вопрос; встретился только как уже существующее (не трогаемое)
  поле `парами` в `застольеДляРейтинга`.
- Фильтр «Друзья» — списка друзей в проекте нет, отдельная большая задача.
- Вторая мера «сила» (`server/сила-игроков.js`) — в задании владельца не
  упомянута отдельно, файл не открывался по заданию; если владелец
  захочет такое же деление по правилу и для силы — это отдельная опись
  и отдельный план по этому файлу.
- `server/билеты.js` (партии с ботом в браузере, вне комнаты) — см.
  открытый вопрос ниже, не трогается без отдельного решения.

## 4. Открытые вопросы — нужно решение владельца/штаба, не только план
1. **Есть ли выбор «подкидной/переводной» в одиночной игре против бота
   (не через комнату по сети)?** Если да — этот путь (`server/билеты.js`)
   сейчас вообще не несёт признак правила и его тоже придётся научить
   передавать, иначе партии с ботом всегда попадут в один и тот же счётчик
   (или ни в один). Это архитектурный вопрос, требует ответа до этапа 1,
   иначе формат `поПравилу` может оказаться неполным.
2. **Дневной потолок очков (12 от ботов, 60 от людей) — общий на все
   правила сразу или отдельный на каждое?** Сейчас потолок считается от
   `запись.очки` (общий счёт). Если завести отдельные под-агрегаты, нужно
   явно решить: тратится ли лимит один раз на партию (и в общий, и в
   под-агрегат), или у под-агрегата свой независимый лимит — от этого
   зависит, можно ли будет накрутить вдвое больше очков, играя попеременно
   в оба правила. Это продуктовое решение, не мне решать самому.
3. **Формат ответа `/рейтинг` при переключении фильтра**: везти ли сразу
   ОБА среза (общий + оба правила) одним ответом, как сейчас везутся
   «очки» и «сила» вместе (см. `сила` внутри `срезДляИгрока`) — тогда
   переключение фильтра на экране не требует нового похода на сервер, как
   уже сделано для меры сила/очки; или спрашивать сервер заново при каждом
   переключении фильтра, как сейчас при смене игры. Первое дороже на
   сервере при каждом ответе (даже если фильтр не открывали), второе —
   лишний поход на сервер при каждом клике. Технически несложно любое,
   но выбор — вопрос штаба, влияет сразу на этапы 1, 3 и 4.

## 4.1 Решения штаба по открытым вопросам (19.09, утверждено к работе)

1. **Бот-партии (`server/билеты.js`) — вне рамок, без правила.** Протокол
   `/итог-с-ботом` уже сегодня сознательно режет из тела запроса всё, кроме
   билета и исхода («Уровень, число ботов и прочее, что браузер мог
   дописать, сюда не передаётся вовсе» — `server/сервер.js:2597`, правило
   «клиенту не верим»). Добавлять туда новое клиентское поле «правило» —
   отдельное архитектурное решение с отдельной ценой доверия, не часть этой
   задачи. Партии с ботом продолжают идти только в общий счёт, как сейчас;
   `поПравилу` у них не растёт ни в одну, ни в другую сторону. Файл
   `server/билеты.js` в этой работе не трогаем.
2. **Суточный потолок — общий на все правила, не отдельный.** Под-агрегат
   `поПравилу` получает ровно ту же сумму очков, что фактически была
   начислена в общий счёт под общим потолком (12 от ботов / 60 от людей) —
   не отдельный лимит на «подкидной» и на «переводной». Так нельзя
   накрутить вдвое, играя попеременно в оба правила. Второй системы
   ограничителей не заводим.
3. **Ответ `/рейтинг` — одним запросом сразу все срезы.** Как сегодня едут
   вместе «очки» и «сила», `срезДляИгрока` отдаёт три среза одним ответом:
   общий, подкидной, переводной. Переключение фильтра на экране не требует
   нового похода на сервер — клиент просто показывает другой уже
   полученный срез. Кэш `последнийОтвет` на экране остаётся ключённым
   только по игре, как сейчас, без изменений логики кэша.
