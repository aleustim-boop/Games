# Система работы штаба — описание для исследования

Написано 13 сентября по просьбе владельца: «опиши свою систему работы, чтобы я провёл исследование, как лучше систематизировать её использование для максимальной выгоды и рационального использования токенов».

---

## 1. Устройство: одна голова, пять рук

**Штаб** — главная сессия (эта). Кода не пишет никогда. Его работа: резать задачи на этапы, писать задания, утверждать планы, принимать работу, гонять проверки чужими руками, коммитить, вести дашборд и очередь, разговаривать с владельцем.

**Исполнители** — отдельные сессии, каждая живёт один этап и умирает:

| Роль | Что делает | Права | Обычная модель |
|---|---|---|---|
| developer | пишет код строго по заданию | только названные файлы | лёгкая (Sonnet); полная — на планы и рискованные места |
| designer | внешний вид | только файлы оформления | полная на большие экраны, лёгкая на уборку |
| reviewer | читает код глазами, ищет ошибки | только чтение, писать нечем | лёгкая; полная — перед перезапуском сервера |
| tester | гоняет игру в браузере и в node | пишет только в tests/ | лёгкая |
| playtester | играет как новичок, ищет непонятность | только браузер, кода не видит | — |

Права урезаны нарочно, чтобы правила держались сами: ревьюер физически не может «поправить по-тихому», плейтестер не может подсмотреть, как задумано.

## 2. Поток работы

```
просьба владельца → запись в очередь (его словами)
→ [большой этап] опись и план отдельным исполнителем → штаб утверждает, план в файл штаб/план-*.md
→ [малый этап] штаб пишет план прямо в задание
→ developer → (designer со снимком) → tester → reviewer → штаб принимает
→ коммит (публикуется сам) → проверка ОПУБЛИКОВАННОГО адреса → запись на дашборд
→ вопрос владельцу в «Важное» с кнопками, если нужен его взгляд
```

Железные правила потока:
- **один файл — один исполнитель**, файлы распределяются вслух в задании;
- **браузерные проверяющие — строго по очереди** (двое в одном браузере дают ложные отчёты);
- **новый файл подключает штаб** тем же коммитом, которым принимает работу;
- **этап с новым экраном не принимается без снимка**, и штаб смотрит снимок сам;
- **каждая проверка обязана уметь краснеть**: к ней делается ломающий запуск, который портит проверяемое и требует провала;
- **время — только из команды** (date, git log, время файла), из головы не пишется никогда;
- **вопросы владельцу — на дашборде** с кнопками (и теперь полем для текста), не в ленте чата;
- **сторожа**: пока штаб ждёт ответа владельца, фоновая программа следит за файлом ответов и будит штаб при нажатии.

## 3. Артефакты (внешняя память системы)

Вся память живёт в файлах, а не в головах сессий — благодаря этому исполнителей можно убивать без потерь:

- `CLAUDE.md` — конституция: правила команды и уроки, писанные кровью, каждый с историей «почему»;
- `ЗАДАЧИ.md` + дашборд — состояние: что в работе, очередь с уровнями (горит/скоро/потом/задел), решения штаба;
- `штаб/важное.json` → «Важное» на дашборде — вопросы владельцу с кнопками и полем, с ответом «чем кончилось»;
- `штаб/план-*.md` — планы больших этапов: опись «как есть», шаги, опасные места, решения;
- `штаб/*.js` — маленькие программы для повторяющихся действий (перезапуск сервера, пересборка дашборда, счёт расхода): одна команда вместо цепочки, одно разрешение вместо потока окон;
- память штаба (уроки) — отдельные заметки: «сделано ≠ доступно», «время не из головы», «лимит съедает длинная память».

## 4. Экономика токенов — где на самом деле деньги

**Главный факт: сама работа почти ничего не стоит.** За последние двое суток написанный исполнителями текст (код + отчёты) — меньше 2% расхода. Всё остальное — **перечитывание собственной памяти на каждом шаге**: каждый вызов инструмента заставляет сессию заново прочитать весь свой контекст. Цена шага растёт линейно с длиной сессии, поэтому длинная сессия к концу стоит в 50–100 раз дороже свежей за тот же шаг.

Свежий срез (12–13 сентября, вес = входы + 1,25·запись кэша + 0,1·чтение кэша + 5·вывод; всего 121,9M):

| Строка | Доля | Запросов | Контекст доходил до |
|---|---|---|---|
| тестировщик (лёгкая модель) | 24,1% | 2176 | 314k |
| **штаб (полная модель)** | **33,8%** (23,0+10,8) | 515 | **923k** |
| разработчик (лёгкая) | 19,2% | 1386 | 392k |
| оформитель (полная+лёгкая) | 20,1% | 1317 | 378k |
| **ревьюер (обе)** | **1,3%** | 86 | 171k |

Что из этого следует:

1. **Штаб — самая дорогая строка**, потому что его сессия самая длинная (сейчас ~920 тысяч) и каждый его шаг перечитывает её всю. Лекарства: /compact от владельца; меньше шагов штаба (одна проверка вместо трёх, пакетные правки записей); не дёргать программы дашборда после каждого чиха.
2. **Тестировщик дорог количеством запросов, а не умом.** 2176 запросов — это браузер: каждый клик и каждый снимок экрана — отдельный запрос с перечитыванием контекста. Один прогон-скрипт на node (`node tests/проверка.js` = один запрос) в сотни раз дешевле часа ручных кликов. Правило выгоды: **браузером проверять только то, что нельзя проверить в node**, и писать постоянные проверки файлами.
3. **Ревьюер — лучшая покупка в системе.** 1,3% расхода, а на его счету: дыра с билетом в «Раздаче дня», карты от чужого игрока, невидимые отказы сервера, кэш-беда с номерами версий. Чтение кода дёшево, потому что не требует ни браузера, ни длинной сессии.
4. **Лёгкая модель почти всегда достаточна** для работы по готовому плану. Полная нужна там, где план ещё не существует (опись, архитектура) и где цена ошибки — боевой сервер.

## 5. Правила экономии, введённые 11 сентября (действуют)

1. Новый этап — новый исполнитель с коротким заданием. Старого с памятью больше ~200k не возвращать: свежий прочтёт нужные файлы дешевле, чем старый сделает один шаг.
2. Возвращать исполнителя можно только сразу (до 5 минут простоя) — потом его память перезаписывается целиком по дорогой цене.
3. Тестировщик и типовые задачи — на лёгкой модели.
4. Параллелим только нужное; сейчас по слову владельца — один исполнитель за раз.
5. Штаб делает меньше мелких шагов.
6. Малую задачу штаб описывает планом сам, без круга «пришли план — жди утверждения».

Проверка расхода: `node штаб/расход.js 2026-09-12T00:00:00` — раз в день, пока лимит тесный.

## 6. Что ещё можно выжать (идеи для исследования)

- **Бюджет запросов тестировщику.** Сейчас ограничиваю минутами («не больше 30 минут»); честнее ограничивать запросами и требовать: сначала автоскрипт, браузер — только на просмотр итога. Гипотеза: −30–50% строки тестировщика.
- **/compact штаба по расписанию.** Контекст штаба за сутки вырастает до ~900k; сжатие в начале дня удешевляет каждый следующий шаг. Это делает только владелец.
- **Реже дёргать программы дашборда.** Сейчас в-работе.js зовётся после каждой смены исполнителя; можно копить и обновлять раз в этап.
- **Шаблоны заданий.** Задание исполнителю — 1–2k токенов текста; постоянные куски (правила команд, запреты, форма отчёта) можно вынести в файлы ролей, а в задании оставлять только суть.
- **Снимки экрана — только необходимые.** Каждый снимок, который штаб смотрит сам, — это тысячи токенов на изображение; смотреть один итоговый на этап, не все двенадцать.
- **Пороговое ревью.** Мелочь без ревью (только проверки), рисковое (сервер, сеть, общие файлы) — всегда с ревью. Так уже делается, стоит закрепить как правило.
- **Час простоя лечится сторожами, а не опросом.** Уже внедрено: фоновые наблюдатели за ответами владельца будят штаб — ноль расхода на ожидание.

## 7. Слабые места, о которых надо знать честно

- Штаб иногда ошибается в механике, которую сам же запретил (дважды вписал время из головы) — лечится правилом «сперва команда, потом запись», записано в память.
- Проверки стареют молча: четыре проверки шашек краснели из-за старой перестройки, и это маскировалось таймаутом. Урок: при каждой перестройке искать проверки по именам затронутых узлов, а не ждать, пока прогон покраснеет.
- «Работает на стенде» ≠ «доехало до игрока»: git-правила и кэш версий дважды прятали от игроков то, что у нас выглядело целым. Теперь проверяется опубликованный адрес.
