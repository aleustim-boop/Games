# Games — игра для Telegram

## Что мы строим

Telegram Mini App — игра, которая открывается прямо внутри Telegram по кнопке в боте.
Играют обычные пользователи Telegram с телефона, поэтому управление — пальцем (тап/свайп),
экран вертикальный, загрузка быстрая.

**Стек (выбран за простоту и нулевую стоимость):**

| Что | Чем | Почему так |
|---|---|---|
| Сама игра | HTML + CSS + чистый JavaScript, карты — обычные элементы страницы (не `<canvas>`) | Ноль сборки: файл открывается в браузере двойным кликом, ошибку видно сразу. Карта — это прямоугольник с текстом, по которому надо попадать пальцем: на обычных элементах нажатия ловятся сами, на `<canvas>` пришлось бы вручную считать, в какую карту ткнули |
| Связь с Telegram | Официальный скрипт `telegram-web-app.js` (Telegram WebApp API) | Даёт тему оформления, кнопки, имя игрока — без своей авторизации |
| Рекорды | `Telegram CloudStorage`, а если его нет — `localStorage` | Рекорды переезжают между устройствами игрока, при этом сервер и база не нужны — значит, платить не за что |
| Бот-лаунчер | Node.js + Telegram Bot API | Одна маленькая программа: показывает кнопку «Играть» |
| Публикация | GitHub Pages (бесплатный HTTPS) | Telegram открывает Mini App только по HTTPS |

**Правило по стеку:** никаких фреймворков и сборщиков (React, Vite, Webpack, Phaser) без
отдельного решения штаба. Если кажется, что без библиотеки не обойтись — это вопрос к штабу,
а не решение исполнителя.

## Когда первая версия считается готовой (Definition of Ready v1)

Первая версия готова, когда всё перечисленное работает:

1. Игра открывается внутри Telegram по кнопке в боте (не только в обычном браузере).
2. Есть стартовое меню: кнопка «Играть», кнопка «Рекорды», выбор сложности.
3. Игровой цикл целиком: старт → игра → проигрыш/победа → экран результата → рестарт без перезагрузки страницы.
4. Есть хотя бы 3 уровня сложности (или растущая сложность внутри одной партии).
5. Рекорды сохраняются и переживают закрытие игры: таблица личных рекордов, минимум 10 строк, с датой.
6. Есть звук: минимум — звук действия и звук проигрыша, с кнопкой выключения звука.
7. Играется на телефоне вертикально, ничего не выезжает за экран, управление пальцем работает.
8. В `README.md` записано, как запустить локально и как подключить к боту.

Пока хотя бы один пункт не выполнен — первой версии нет.

## Язык

- **Всё общение, комментарии в коде, коммиты, документация и тексты в самой игре — на русском.**
- Объясняем простым языком, как для человека без технического образования: без жаргона,
  а если термин необходим — сразу расшифровываем его в скобках.
- Плохо: «зарефакторил стейт-менеджмент, вынес в отдельный модуль».
  Хорошо: «разделил файл на два: в одном правила игры, в другом отрисовка — так проще искать ошибки».

## Как работает команда

### Штаб (лид)

Штаб — это главная сессия. Штаб **не пишет код сам**. Его работа:

1. Разбивает задачу на маленькие этапы (один этап = один-два файла, максимум пара часов работы).
2. Ставит задачу исполнителю: что сделать, в каких файлах, что считается результатом.
3. **Утверждает план до начала работы.** Исполнитель без утверждённого плана код не пишет.
4. Принимает работу: смотрит отчёт исполнителя, отправляет результат на проверку ревьюеру.
5. Решает спорные вопросы: выбор стека, структура файлов, что входит в первую версию.
6. Делает git-коммит после каждого принятого этапа.

Если штаб поймал себя на том, что пишет код руками — это ошибка процесса, задачу нужно отдать исполнителю.

### Исполнители

| Роль | Что делает | Что может менять |
|---|---|---|
| `developer` | пишет код строго по утверждённому плану, малыми шагами, докладывает штабу | файлы, которые назвал штаб |
| `designer` | внешний вид: читаемость карт, понятность экрана, попадание пальцем | только `style.css` |
| `reviewer` | читает код и ищет ошибки глазами | ничего, инструментов на запись у него нет |
| `tester` | запускает игру в браузере и гоняет сотни автопартий, ищет поломки | только `tests/` |
| `playtester` | играет как новичок и ищет непонятность, а не поломки | ничего, кода не видит вовсе |

Права выданы так, чтобы правила держались сами, а не на дисциплине:

- у `reviewer` нет инструментов записи — он не сможет «поправить на месте» и незаметно
  подменить проверку правкой;
- у `playtester` нет доступа к коду вообще, только браузер — поэтому его «я не понял»
  честное, а не догадка человека, подсмотревшего, как оно задумано;
- у `designer` и `tester` инструменты записи есть, поэтому их границы держатся правилом —
  за ними штаб следит отдельно.

### Железное правило: один файл — один исполнитель

Два исполнителя **никогда** не редактируют один и тот же файл одновременно.
Штаб перед запуском параллельных задач вслух распределяет файлы:

> «Исполнитель А работает только с `src/game.js`. Исполнитель Б — только с `src/ui.js`.
> Общий файл `src/storage.js` сейчас не трогает никто.»

Если исполнителю по ходу дела понадобился чужой файл — он **останавливается и спрашивает штаб**,
а не правит сам. Штаб либо ставит задачи по очереди, либо переназначает файл.

### Ритм работы

```
Штаб ставит задачу → исполнитель присылает план → штаб утверждает план →
исполнитель делает малыми шагами → отчёт штабу → проверка ревьюером →
штаб принимает → git-коммит → следующий этап
```

### Штаб обязан следить, что работа идёт

**Молчание исполнителя — это не признак прогресса.** Исполнитель может встать по трём
причинам, и ни одна из них сама о себе не сообщит: его прервали вручную, он упёрся в запрос
разрешения, он завис на одной проблеме.

Поэтому запустил исполнителя — сразу ставь контрольную точку:

1. **Скажи вслух, чего ждёшь и когда.** «Ожидаю `js/game.js` примерно через час» —
   в отчёте штаба это должно быть написано прямым текстом, чтобы просрочку было видно.
2. **Проверяй по файлам, а не по ощущениям.** Признак живой работы один: файлы из задачи
   растут, время последней правки свежее. `git status` и время изменения файла — вот и вся проверка.
3. **Не отчитывайся пользователю фразой «работа идёт», если ты этого не проверил.**
   Проверил — говори что видишь: какие файлы появились, когда правились последний раз.
4. **Просрочил вдвое — считай, что встал.** Не жди дальше: выясняй причину и перезапускай.

Отдельно: система настроена сообщать штабу о каждой остановке исполнителя (хук `SubagentStop`
в `.claude/settings.local.json`). Пришёл такой сигнал — немедленно проверь файлы и отчёт.
Сигнал приходит и когда исполнителя прервали вручную, а такое молчание выглядит точно так же,
как работа.

**Прерванного исполнителя не перезапускай молча.** Пользователь мог остановить его нарочно.
Доложи, что уцелело и чего не хватает, и спроси, продолжать ли.

### Двух проверяющих в браузер одновременно не пускать

Браузер у проверяющих общий. Если запустить `tester` и `playtester` вместе, они лезут в одну
страницу: один замораживает игру, чтобы померить вёрстку, а второй в этот момент видит
«игра зависла» и записывает несуществующую поломку. Проверено на своей шкуре — так был
получен целый ложный отчёт о зависаниях.

Правило: **браузерные проверяющие работают по очереди.** Сначала один, дождался отчёта —
запускай второго. Параллелить можно только тех, кто в браузер не ходит.

Отдельно: у `playtester` нет инструментов запуска команд, а браузер-робот не открывает файлы
с диска напрямую. Поэтому **штаб обязан заранее поднять локальный сервер и дать ссылку вида
`http://…`** — иначе исполнитель просто не сможет начать.

### Коммиты

После каждого принятого этапа — коммит с понятным описанием на русском, из которого
человек через месяц поймёт, что изменилось.

- Хорошо: `добавил сохранение рекордов в CloudStorage с откатом на localStorage`
- Плохо: `фиксы`, `wip`, `update game.js`

Коммит делает штаб — после того, как этап принят. Незаконченную работу не коммитим.

## Definition of Done (когда этап считается сделанным)

Этап принят, только если выполнены **все три** условия:

1. **Код запускается.** Игра открывается, консоль браузера без красных ошибок, ничего не сломано из того, что работало раньше.
2. **Есть минимальная проверка работоспособности.** Исполнитель описал в отчёте конкретные шаги: «открыл `index.html`, нажал "Играть", набрал 3 очка, проиграл, увидел экран результата, рекорд появился в таблице». Проверка должна быть повторяемой — штаб может пройти её сам.
3. **Штаб принял результат.** Замечания ревьюера либо исправлены, либо штаб их сознательно отложил и записал это в задачу.

Не выполнено хотя бы одно — этап возвращается исполнителю, коммита нет.

## Структура проекта

```
Games/
├── CLAUDE.md          # этот файл — правила команды
├── README.md          # как запустить и как подключить к боту
├── .gitignore
├── index.html         # разметка: три экрана — меню, стол, результат
├── style.css          # весь внешний вид (файл дизайнера)
├── .claude/
│   ├── agents/        # роли: developer, designer, reviewer, tester, playtester
│   └── settings.local.json   # доступы и сигнал об остановке исполнителя (вне git)
├── js/
│   ├── game.js        # правила игры, бот, отрисовка стола
│   ├── telegram.js    # связь с Telegram: saveScore(n), loadScore(), isReady()
│   └── сеть.js        # игра вдвоём: разговор с сервером комнат
├── server/            # сервер комнат для игры вдвоём (Node.js, без библиотек)
│   ├── сервер.js      # HTTP-двери: создать, войти, ход, что-нового
│   ├── комнаты.js     # комнаты, коды из четырёх знаков, пропуска игроков
│   ├── партия-по-сети.js  # партия на сервере: чей ход и что видит каждый
│   └── шлагбаум.js    # тормозит подбор чужих кодов комнат
├── tests/             # проверки (файлы тестировщика)
└── bot/               # бот-лаунчер на Node.js, токен в bot/.env (вне git)
```

**Договор с Telegram:** `js/telegram.js` даёт наружу ровно три функции —
`saveScore(n)`, `loadScore()`, `isReady()`. Файл `js/game.js` пользуется только ими и больше
ничего про Telegram не знает. Так две половины можно писать одновременно и они состыкуются.

**Договор с сетью:** такая же граница проведена и вокруг игры вдвоём. `js/сеть.js` —
единственное место в браузере, которое знает про сервер, коды комнат и пропуска.
Наружу он даёт `window.Сеть` (главное там — `отправитьХод` и `покинутьПартию`), а готовое
состояние стола отдаёт обратно одной дверью — `ИграПоСети.показатьВид`. Файл `js/game.js`
про HTTP, коды и пропуска не знает вовсе: он получает состояние и рисует стол — тот же,
что и в игре с ботом.

**Правила игры не раздваиваются.** Сервер берёт их из того же `js/game.js`, что и браузер
(см. `server/партия-по-сети.js`). Это сделано нарочно: иначе сервер и игра однажды разойдутся
в решениях, и такую ошибку будут искать неделю. Правишь правила — помни, что правишь их
сразу для обеих сторон.

**Клиенту не верим.** Всё, что уходит игроку по сети, собирается вручную поле за полем
в одном месте — `видДляИгрока` в `server/партия-по-сети.js`. Рука соперника, колода и отбой
выходят оттуда только числами. Появилось новое поле в ответе сервера — добавлять его туда,
и никуда больше: тогда утечку чужих карт всегда есть где искать.

## Безопасность

Токен бота и любые ключи — только в файле `.env`, который не попадает в git.
В коде и в чате токены не пишем никогда. Нужен новый секрет — спрашиваем пользователя.
